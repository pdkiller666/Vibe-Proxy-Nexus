# Ограничение устройств без поломки VLESS-over-WebSocket

## Принятое решение

Ограничение применяется на уровне управления ключами, а не на уровне
транспортных соединений:

- один активный VLESS UUID = один слот устройства;
- количество одновременно выданных ключей проверяется по
  `devicesIncluded + extraDeviceSlots` активной подписки;
- новый ключ выдаётся только при свободном слоте;
- отзыв ключа освобождает слот, а перевыпуск создаёт новый UUID;
- один и тот же UUID может открыть столько параллельных WebSocket-туннелей,
  сколько нужно обычному VPN-клиенту.

Это совместимо с Happ, v2rayNG и v2rayN: клиенты могут держать несколько
параллельных VLESS-over-WebSocket потоков для одной загрузки страниц, HTTP/3
fallback и фоновых запросов. Ограничение raw WebSocket на UUID применять нельзя.

Важно: это политика выдачи слотов, а не доказательство физической
идентичности устройства. Если пользователь вручную скопировал один VLESS-ключ
на два телефона, текущая архитектура намеренно не пытается отличить эти
телефоны. Такая проверка потребовала бы IP-сигнала, поддержанного Xray
ограничителя, gateway/реестра сессий или другого механизма вне согласованных
ограничений.

## Что не является решением

Поле `limitIp: 1` оставлено только как совместимый hint для возможного
кастомного Xray-образа. В используемом vanilla Xray оно не является
надёжным ограничителем и не должно использоваться как гарантия.

Нельзя возвращать:

- `sid` в путь WebSocket;
- Nginx `limit_conn` по query-параметру;
- реестр активных raw WebSocket-сокетов в Node.js;
- ограничение количества transport-соединений через Xray.

Один телефон создаёт много таких соединений. Второе transport-соединение не
означает второе устройство, поэтому его отклонение оставляет Happ визуально
подключённым, но ломает загрузку сайтов.
