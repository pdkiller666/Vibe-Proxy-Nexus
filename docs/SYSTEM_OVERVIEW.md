# Обзор системы VPNexus — как всё работает

> Этот документ описывает работающее поведение системы с точки зрения пользователя,
> оператора и разработчика. Актуален по состоянию на август 2026.
> Для структуры кода — см. `PROJECT_MAP.md`. Для технических уроков — см. `.agents/memory/`.

---

## Инфраструктура

### Хостинг и контейнер

Продакшен разворачивается **одним Docker-образом** на Amvera Cloud. В контейнере живут:

- **Node.js (Express)** — API + отдача статики фронта
- **Xray-core** — локальная VPN-нода
- **supervisord** — управляет обоими процессами

Контейнер слушает порт 443. Amvera терминирует TLS на своём балансировщике и проксирует
HTTP-трафик в контейнер. Сырой TCP (Reality / VLESS TCP) невозможен без Dedicated IPv4 —
Amvera не пробрасывает нетиповые порты.

### Транспорт VPN

**VLESS + WebSocket + TLS** поверх обычного HTTPS-домена:

- Путь WebSocket: `/vpnws` (Node.js проксирует апгрейд на `127.0.0.1:10000` — локальный Xray inbound)
- TLS терминируется на балансировщике Amvera, внутри контейнера HTTP

### Домены

| Домен | Назначение |
|---|---|
| `vpnexus.pro` | Основной пользовательский домен |
| `*.amvera.tech` | Технический резервный домен Amvera |

Активный домен выбирается сервером через `payment_settings.primaryDomain` + healthz-check.
Ссылки генерируются per-request — при смене домена все существующие подписки начнут отдавать
новый домен автоматически, без переиздачи ключей.

### VPN-ноды

| Тип | Признак | Как управляется |
|---|---|---|
| Локальная (Amvera) | `vpn_nodes.managementApiUrl IS NULL` | Конфиг пишется на диск, Xray читает напрямую |
| Удалённая VPS | `managementApiUrl` заполнен | Management REST API на каждом VPS |

При удалении ноды активные ключи автоматически мигрируют на другую ноду (сначала тот же регион,
затем глобально). Ответ содержит `migratedKeys` и `failedMigrations`.

## VPN-ключи

### Модель

Каждый ключ = UUID в Xray. Биллинг считает трафик по UUID через `QueryStats` gRPC.  
Один ключ = одно устройство (`limitIp: 1` в Xray — один одновременный IP).

Ключ привязан к конкретной ноде. При смене сервера (`relocate`) новый ключ выпускается
на целевой ноде, старый отзывается — пользователь получает тот же UUID-схожий опыт через подписку.

### Выдача и отзыв

- **Выпуск:** проверяется лимит устройств тарифа + свободные слоты ноды. Для admin — обход лимитов.
- **Отзыв:** сначала пишется `revokedAt` в БД, затем Xray (если Xray недоступен — не критично).
- **Авто-отзыв:** при истечении подписки, исчерпании баланса (почасовой), превышении лимита трафика.
- **Авто-восстановление (`ensureActiveKeyForUser`):** при продлении/пополнении — если у пользователя
  нет ни одного активного ключа, ключ перевыпускается автоматически.

## Форматы подписки

Единственный публичный endpoint: `GET /api/sub/:token`

### Токен

Stateless HMAC: `userId.sha256(userId, SESSION_SECRET)`. Не хранится в БД.
Меняется только при смене `SESSION_SECRET` (разово инвалидирует все подписки).

### Форматы по параметру `?format=`

| URL | Что возвращает | Поддерживаемые клиенты |
|---|---|---|
| *(без параметра)* | Base64-список `vless://` URI | Все клиенты: Happ, v2rayNG, Streisand, v2rayN, V2Box |
| `?format=xray` | Xray JSON-конфиг, все активные ключи пользователя | Happ, v2rayN |
| `?format=xray&key=<id>` | Xray JSON одного устройства, `Profile-Title` = имя устройства | Happ, v2rayN |

### Xray JSON — правила маршрутизации (RF-обход)

Правила встроены в сам конфиг, не зависят от настроек клиента:

- `geoip:ru` → direct (российские IP-диапазоны)
- Домены `.ru`, `.рф` → direct
- Яндекс, ВКонтакте, Сбер на нероссийских доменах → direct
- Всё остальное → туннель

**Важно для Happ:** ядро должно быть `Xray core`, встроенная маршрутизация (`Routing`) должна
быть **выключена** — иначе правила Happ перекрывают правила конфига.

### Заголовки ответа подписки

```
Subscription-Userinfo: upload=...; download=...; total=...; expire=...
Profile-Update-Interval: Xh
Profile-Title: base64:<название>     # для ?format=xray&key=<id>
Content-Disposition: attachment; filename="vpnexus.json"
```

Клиенты (Happ, v2rayN) автоматически обновляют подписку по интервалу из заголовка.

## Тарифы и биллинг

### Типы тарифов

| Тип | `billingType` | Как активируется | Как списывается |
|---|---|---|---|
| Пробный | `monthly` | Автоматически при регистрации | Бесплатно (`priceRub=0`) |
| Ежемесячный | `monthly` | Через оплату | Разово при активации |
| Почасовой | `hourly` | Из баланса | Каждый час с баланса |
| Промо | `monthly`/`hourly` | Только через инвайт | По цене плана |

Промо-тарифы (`isPromo=true`) скрыты из публичного `GET /api/plans`.
Видны только в admin-панели и появляются в дропдауне при создании инвайта.

### Жизненный цикл подписки

```
Оплата подтверждена
  → confirmPayment(): startsAt/endsAt, текущая активная подписка уходит в архив атомарно
  → если пользователь на почасовом — новая подписка ставится в очередь (startsAt = текущей endsAt)
  → ensureActiveKeyForUser() — если ключей нет, перевыпустить

Каждый час (hourlyBilling):
  → UPDATE subscriptions SET last_billed_at = now() WHERE last_billed_at < now() - interval '1h'
  → оптимистичная блокировка по affected rows (защита от гонок)
  → если баланса не хватает → подписка истекает → ключи отзываются

Каждые N минут (subscriptionLifecycle):
  → истёкшие подписки → ключи отзываются, статус обновляется
```

### Дополнительные слоты и трафик

- **Доп. устройство:** покупается через `POST /api/extra-slot-orders`, оплата → слот добавляется
  на текущую подписку (истекает вместе с подпиской)
- **Доп. трафик:** аналогично — `extraTrafficGb` добавляется к лимиту плана
- **Эффективный лимит трафика в `/me`:** `plan.trafficLimitGb + subscription.extraTrafficGb`

## Способы оплаты

### YooMoney (автоматический)

1. Фронт открывает QuickPay-ссылку с `label=paymentId`
2. После оплаты YooMoney шлёт HMAC-вебхук на `/api/yoomoney/webhook`
3. Сервер проверяет подпись + сумму (в копейках) → `confirmPaymentById()`

### СБП (ручной)

1. Пользователь переводит деньги по QR/ссылке из настроек
2. Загружает скриншот (JPEG/PNG/WebP, max 8 МБ base64, проверяется magic bytes)
3. Нажимает «Я оплатил(а)»
4. Администратор видит платёж в очереди → подтверждает → `confirmPaymentById()`

### Настройки оплаты (admin)

Управляются через `PATCH /api/admin/payment-settings`:

- `yookassaEnabled` / `sbpEnabled` — показ тайлов выбора метода
- `sbpPaymentUrl` — прямая ссылка для СБП-приложения
- `sbpQrCodeData` — QR-изображение (хранится в Postgres base64, отдаётся бинарно)
- `showManualSbpDetails` — показывать ли блок с реквизитами (номер/банк/получатель)
- `primaryDomain` — какой домен использовать в ссылках подписки
- `extraDeviceSlotPriceRub` — цена доп. устройства
- `allowFreeExtraDeviceSlot` — разрешить бесплатный первый доп. слот

## Мониторинг трафика

Polling через gRPC `QueryStats` с `reset: false`:

- Счётчики не сбрасываются на стороне Xray — сервер хранит `lastSeen` и считает дельту
- При рестарте Xray данные не теряются (дельта от нового нуля = весь трафик)
- Flush-вызовы сериализованы через очередь — защита от двойного кредитирования при параллельных опросах

## Безопасность

| Аспект | Реализация | Статус |
|---|---|---|
| Хэши паролей | scrypt `N=16384` | ✅ (N=65536 вызывает OOM на Amvera) |
| Сессии | SHA-256 хэш токена в БД + `expiresAt` | ✅ |
| Токены сброса пароля | SHA-256 хэш в БД, одноразовые | ✅ |
| Скриншоты | MIME allowlist + magic-byte check + 8 МБ cap | ✅ |
| Выпуск ключей | `SELECT FOR UPDATE` — защита от гонок | ✅ |
| Почасовой биллинг | Оптимистичная блокировка по `last_billed_at` | ✅ |
| Rate-limiting | In-memory (сбрасывается при рестарте) | ⚠️ не персистентный |
| CSRF | Не реализован | ❌ |
| Docker USER | Контейнер запускается от root | ⚠️ низкий приоритет |

## Что было проверено и не подошло

### Sing-box selector (август 2026)

Попытка реализовать «одна подписка → дропдаун выбора устройства» через Sing-box `selector` outbound.

**Результат:** Happ работает только на Xray-движке (переключения на Sing-box нет).
Тип `selector` Xray не знает → ошибка парсинга конфига. Код добавлен и убран в тот же день.

**Текущее решение:** per-device Xray-ссылки (`?format=xray&key=<id>`) с именем устройства
в `Profile-Title` — каждое устройство видно отдельной карточкой в Happ с понятным именем.
