| # | Пункт кодера | Моё мнение |
| :--- | :--- | :--- |

| 3 | guard 60 с без индекса | **Согласен.** На текущем масштабе — приемлемо; фиксируем триггер будущей оптимизации, а не задачу. |
| 4 | технические ошибки autoRenew не глотать | **Согласен.** Разделяем business-402 и technical-500; последние — в лог + admin-событие, ретрай в следующем прогоне. |
| 5 | кнопка для нулевых/promo-планов | **Согласен.** UI-фильтр + API-400 как backstop — двойная защита. |

**Почему reconciler лучше в коде, а не в `entrypoint.sh`:** в проекте уже есть паттерн startup-джобов на TypeScript — `seedAdmin.ts` и `backfillReferralCodes.ts` выполняются при старте контейнера. Reconciler в TS получает атомарность транзакции «reject + refund» из коробки и покрывается Vitest-тестами, чего shell-SQL не даст. Амвера-деплой = рестарт контейнера = reconciler сработает именно в тот момент, когда нужен (после краха). Плюс лёгкий интервал для полноты.

**Почему reconciler безопасен (аргумент для уверенности):** `confirmPaymentById` атомарен — если он успел выполниться, платёж уже `confirmed`. Значит, баланс-платёж в статусе `pending` старше 5 минут — **гарантированно** неподтверждённый (нормальный разрыв tx1→confirm — миллисекунды). Порог 5 минут на порядки выше нормы → ложных срабатываний быть не может.

## 📝 ТЗ v2.1 — финальные поправки (вшить в документ)

### Поправка 1 → §2 (БД): enum-миграция обязательна
- `lib/db/src/schema/payments.ts`: добавить `"balance"` в массив enum-значений provider.
- `heal-schema.mjs` — **обязательный** блок (имя типа подставить из схемы):
```sql
DO $$ BEGIN
  ALTER TYPE payment_provider ADD VALUE IF NOT EXISTS 'balance';
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
```
- Это шаг №1 порядка работ, до `balanceCheckout.ts`.

### Поправка 2 → новый §4.5: Reconciler зависших balance-платежей
Новый файл `src/lib/reconcileBalancePayments.ts`:
- вызов при старте в `app.ts` (паттерн `backfillReferralCodes.ts`) + интервал 10 мин;
- логика (одна атомарная транзакция на платёж):
```
UPDATE payments SET status='rejected', rejectionReason='balance_reconciled'
WHERE provider='balance' AND status='pending'
  AND created_at < now() - interval '5 minutes'
RETURNING id, user_id, amount_rub
→ для каждой возвращённой строки в той же tx:
  вернуть баланс + INSERT balance_transactions(type='refund', paymentId)
→ logger.warn с деталями
```
- идемпотентность по построению (UPDATE с условием `status='pending'`);
- порог — именованная константа `STALE_BALANCE_PAYMENT_MS`.

### Поправка 3 → §4.1 (guard): документированный лимит
Guard 60 с остаётся без индекса. В комментарий кода и PROJECT_MAP: «при росте balance-платежей до ~10⁴ строк добавить частичный индекс `(user_id, created_at) WHERE provider='balance'` через heal-schema». Сейчас — не задача.

### Поправка 4 → §4.3 (autoRenew): классификация ошибок
```
catch (e):
  если бизнес-ошибка (недостаточно средств)  → штатный auto_renew_failed (дедуп 24 ч)
  иначе (техническая)                        → logger.error + admin system event
      "auto_renew_error" {userId, planId, message} (дедуп 24 ч),
      подписка остаётся в выборке → ретрай через час
```

### Поправка 5 → §5 (UI): фильтр нулевых цен
Компонент `pay-from-balance-button.tsx` не рендерится при `priceRub === 0` (trial/promo) и для hourly; для slot/traffic — при нулевой цене настройки. API-400 из §3.2 остаётся backstop.

## 🟢 Решение

**Поехали.** Порядок работ, предложенный кодером, подтверждаю с поправкой 2 в цепочке:

1. heal-schema (enum) + схема БД (2 столбца + enum) →
2. `balanceCheckout.ts` + роут →
3. `reconcileBalancePayments.ts` →
4. `autoRenew.ts` + тумблер в `me.ts` →
5. фронтенд (компонент + 4 страницы) →
6. тесты (10 сценариев из v2 + 2 новых: reconciler-краш и reconciler-идемпотентность) →
7. деплой с флагом off → смоук → флаг on.

*Перекодируй кодеру дословно: «ТЗ v2.1 принято, все пять поправок обязательны, стартуем с heal-schema. Рефакторинг рабочих биллинг-модулей по-прежнему запрещён — при обнаружении необходимости отступаем от ТЗ только через согласование».* Это последняя страховка от сползания обратно к рискам v1.
