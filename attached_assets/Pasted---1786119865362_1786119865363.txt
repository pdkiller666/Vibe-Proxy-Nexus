Отличный вопрос, и осторожность здесь оправдана: биллинг — это то место, где «рефакторинг ради красоты» стоит дороже всего. После разговора с кодером я пересобрал решение по принципу **минимального вторжения**: новая функциональность не модифицирует рабочие модули, а **надстраивается тонким адаптером поверх уже протестированной воронки подтверждения платежей**.

---

## 🔑 Ключевая идея: не строить параллельный биллинг — войти в существующую воронку

В проекте уже есть **одна точка, через которую проходит всё**: `confirmPaymentById()` из `lib/confirmPayment.ts`. Через неё идут и ЮMoney-вебхуки, и ручные подтверждения админа. Именно она умеет: активировать подписку с честной цепочкой `startsAt/endsAt`, начислять реферальную комиссию, выдавать слоты/трафик, идемпотентно и транзакционно.

Значит, «оплата с баланса» — это **не новая ветка биллинга**, а просто новый способ *создать и сразу подтвердить* платёж:

```
НОВЫЙ изолированный модуль balanceCheckout (≈150 строк)
│
│  tx1 (новая, простая): lock user → проверка баланса →
│      создать payment(pending, provider='balance') →
│      списать баланс + balance_transactions(debit)
│
│  вызов БЕЗ ИЗМЕНЕНИЙ:
▼
confirmPaymentById(paymentId)   ← существующая, нетронутая
│
├─ активация подписки / слота / трафика
├─ реферальная комиссия
└─ история, аналитика, админка — всё работает автоматически
│
│  при ошибке confirm: tx2-компенсация →
│      payment=rejected + balance_transactions(refund)
```

**Всё downstream (ключи, комиссии, цепочки продления, админ-история) продолжает работать без единой правки**, потому что для системы это «обычный подтверждённый платёж».

## 📋 Что изменяется vs что НЕ трогается

### Изменяется (маленький, изолированный дифф)

| Элемент | Изменение | Риск |
| :--- | :--- | :--- |
| `routes/balanceCheckout.ts` + `lib/balanceCheckout.ts` | **Новые файлы** — тонкий оркестратор: списание → `confirmPaymentById` → компенсация при ошибке | 🟢 Нулевой для старого кода |
| `openapi.yaml` | `+ "balance"` в enum `PaymentProvider` + один новый эндпоинт `POST /api/balance-checkout` | 🟢 Кодген по регламенту |
| `users` | `+ auto_renew_from_balance boolean default false` | 🟢 Простой столбец, `drizzle-kit push` без промптов (heal-schema не нужна) |
| `payment_settings` | `+ balancePaymentsEnabled boolean` — **feature flag** | 🟢 Синглтон, паттерн уже есть |
| `app.ts` | +1 строка: регистрация нового джоба автопродления | 🟢 |
| UI | Один переиспользуемый компонент кнопки «Оплатить с баланса» на 3 checkout-страницах + тумблер в профиле | 🟢 Изолированные компоненты |

### НЕ трогается (принципиально)

- ❌ `subscriptions.ts`, `extraSlotOrder.ts`, `extraTrafficOrder.ts` — старые checkout-флоу;
- ❌ `confirmPayment.ts` — никакой вынос «общих функций», никакого рефакторинга;
- ❌ `subscriptionLifecycle.ts` (джоб истечения) — **главный источник риска в старом ТЗ исключён**;
- ❌ `hourlyBilling.ts`, `xray.ts`, `keyIssuance.ts`, админ-роуты.

## 🔄 Автопродление — аддитивно, а не модификацией

Вместо правки джоба истечения — **новый независимый джоб** `autoRenewJob` (раз в сутки):

1. Найти active monthly-подписки с `endsAt` в ближайшие 24 ч, где `autoRenewFromBalance = true`;
2. **Guard от двойного продления:** пропустить, если у пользователя уже есть активная подписка с `startsAt >= endsAt` текущей (т.е. автопродление уже сработало);
3. Вызвать тот же `balanceCheckout` → успех = продление по штатной цепочке; не хватает средств = **ничего не делать** — штатный джоб истечения позже отработает как обычно.

Джоб истечения даже не узнает о существовании автопродления. Сломать продление/истечение невозможно по построению.

## 🛡️ Предохранители (управление риском)

1. **Feature flag** `balancePaymentsEnabled` в `payment_settings`: выключается из админки за секунду, без деплоя и отката. Релиз = включили флаг → проверили → живём.
2. **Поэтапный rollout:** сначала «доп. трафик/слоты с баланса» (самое дешёвое и необратимое-безопасное) → затем monthly → затем автопродление. Каждый этап — за своим флагом.
3. **Компенсация вместо вложенных транзакций:** списание и подтверждение — последовательные tx; при сбое confirm — автоматический `refund` (тип транзакции **уже существует** в enum). Никаких savepoint-сюрпризов.
4. **Двойной клик/ретраи:** кнопка дизейблится после клика (фронт) + серверный guard «уже есть confirmed balance-платёж по этому заказу за последние 60 с → вернуть его». Без новых уникальных индексов и heal-schema.
5. **Отдельная ветка тестов** только для нового модуля: 6–8 сценариев (хватает/не хватает/гонка/компенсация/автопродление/guard). Старые тесты не меняются — это и есть индикатор, что мы ничего не сломали.

## ⚖️ Сравнение подходов

| Параметр | ТЗ v1 (полное) | Lite-адаптер |
| :--- | :--- | :--- |
| Изменённых файлов backend | 6–8 рабочих модулей | **2 новых файла + 1 строка** |
| Правка джоба истечения | Да | **Нет** |
| Рефакторинг confirmPayment | Да | **Нет** |
| Миграции | столбец + уникальный индекс (heal-schema) | **1 безопасный столбец + флаг** |
| Откат | Частичный, болезненный | **Флаг в админке, мгновенно** |
| Оценка | 3–5 дней | **1–1.5 дня с тестами** |
| Риск для работающего биллинга | Средний/высокий | **Практически нулевой** |

---

## 💬 Что честно отдаём в обмен на безопасность

- Нет комбинированной оплаты «баланс + доплата СБП» (и не планировалось в v1);
- Автопродление срабатывает за 24 ч до конца, а не в секунду истечения (это скорее плюс: пользователь не видит разрыва);
- Админка видит balance-платежи как обычный provider «Баланс» без отдельной аналитической разбивки (добавится позже, аддитивно).

**Полное ТЗ v1 не выбрасывайте** — это целевая архитектура на будущее. Но сейчас правильный ход — поставить адаптер, проверить на живом трафике и только потом, при реальной потребности, углублять интеграцию.

*Если нужно — перепишу ТЗ под эту lite-схему в формате «готово к передаче кодеру»: с сигнатурами, списком файлов и чек-листом приёмки.*
