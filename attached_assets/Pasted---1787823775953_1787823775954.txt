## 🛠 Фаза 2: Фикс критических проблем (2-3 дня)

### Проблема 2.1: Сброс учёта трафика после блокировки (P0)

**Симптом:**
Пользователь с лимитом 5 ГБ тратит 6 ГБ → блокировка → докупка 5 ГБ → получает возможность потратить ещё 10 ГБ (вместо 4 ГБ).

**Корень:**
```typescript
// trafficPolling.ts (псевдокод)
const usage = await db
  .select({ total: sum(periodUpBytes + periodDownBytes) })
  .from(vpnKeysTable)
  .where(isNull(revokedAt));  // ← отозванные ключи исключены
```

**Решение:**
1. Добавить поле `cumulativeTrafficBytes` в `subscriptionsTable`
2. В `trafficPolling.ts`:
   - Читать дельту с активных ключей
   - Атомарно добавлять к `cumulativeTrafficBytes`
   - Обнулять `periodUpBytes`/`periodDownBytes` (чтобы не считать дважды)
3. Проверку лимита делать по `cumulativeTrafficBytes`, а не по сумме ключей

**Acceptance criteria:**
- [ ] Миграция БД: добавить `cumulative_traffic_bytes` с default 0
- [ ] Backfill: суммировать periodBytes по активным ключам для существующих подписок
- [ ] Тест: "Докупка после блокировки даёт ровно купленный объём"
- [ ] Тест: "Cumulative накапливается через несколько периодов"
- [ ] Админ-панель показывает cumulative расход в статистике подписки

---

### Проблема 2.2: Гонка между докупкой и проверкой лимита (P0)

**Симптом:**
1. Проверка лимита читает старый лимит (5 ГБ)
2. Пользователь докупает трафик (лимит → 10 ГБ)
3. Старая проверка продолжает работу и блокирует уже восстановленный ключ

**Корень:**
Проверка лимита и докупка не синхронизированы общей блокировкой.

**Решение:**
Использовать `pg_advisory_xact_lock(subscriptionId, magicNumber)` в обеих операциях:

```typescript
// trafficPolling.ts
await tx.execute(
  sql`SELECT pg_advisory_xact_lock(${subscriptionId}, 42)`
);

// balanceCheckout.ts (докупка трафика)
await tx.execute(
  sql`SELECT pg_advisory_xact_lock(${subscriptionId}, 42)`
);
```

**Acceptance criteria:**
- [ ] Advisory lock добавлен в проверку лимита
- [ ] Advisory lock добавлен в докупку трафика
- [ ] Тест: "Параллельные докупка и проверка не создают ложных блокировок"
- [ ] Тест: "Докупка всегда успевает увеличить лимит до следующей проверки"

## 🔧 Фаза 3: Фикс высокоприоритетных проблем (1-2 дня)

### Проблема 3.1: Retry queue для отзывов на недоступных нодах (P1)

**Симптом:**
При превышении лимита ключ отзывается в БД, но если нода недоступна — ключ продолжает работать на Xray.

**Решение:**
1. Добавить таблицу `pending_key_revocations`:
   ```typescript
   {
     id: serial,
     keyId: integer,
     nodeId: integer,
     uuid: text,
     attempts: integer (default 0),
     lastAttemptAt: timestamp,
     createdAt: timestamp
   }
   ```
2. В `revokeKey`: при ошибке удаления из Xray → добавить в retry queue
3. Job `retryPendingRevocations` (каждые 5 минут):
   - Читать записи с `attempts < 5`
   - Пытаться удалить из Xray
   - Успех → удалить из очереди
   - Неудача → увеличить attempts

**Acceptance criteria:**
- [ ] Таблица `pending_key_revocations` создана
- [ ] `revokeKey` пишет в retry queue при ошибке
- [ ] Job `retryPendingRevocations` запускается каждые 5 минут
- [ ] Админ-панель: раздел "Ожидающие отзывы" с количеством попыток
- [ ] Тест: "Отзыв добавляется в retry queue при недоступной ноде"
- [ ] Тест: "Запись удаляется из retry queue после успешного отзыва"
- [ ] Тест: "Запись удаляется после 5 неудачных попыток"
