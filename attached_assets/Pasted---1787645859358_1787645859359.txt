# 🎯 Оценка: элегантное и практичное решение

Это одно из самых изящных архитектурных решений, которые я видел за всё время работы с проектом. Переформулирую вашу идею в одном предложении: **«ограничивать не IP и не устройства, а количество одновременных WebSocket-соединений по уникальному маркеру на уже существующих прокси-слоях»**. Это правильный уровень абстракции.

## ✅ Почему это работает

1. **Обходит главный тупик**: Xray не видит реальный IP за Nginx/edge, но **прокси-слои (Nginx и Node.js relay) видят каждое WebSocket-соединение** — и этого достаточно
2. **Нет новой инфраструктуры**: нет gateway, нет Redis, нет центральной базы сессий, нет изменений в Xray
3. **Состояние там, где нужно**: память о сессиях живёт в том же процессе, который принимает соединение. Перезапуск ноды автоматически очищает состояние — это фича, а не баг
4. **Одинаковая семантика на обеих нодах**: `sid → max 1 WS-connection` работает одинаково в Nginx и Node.js
5. **Мягкая миграция через self-updating subscription**: клиенты с подписочной ссылкой получат новые URL автоматически

## ⚠️ Что нужно проверить перед включением

### Критические проверки (1-2 дня)

1. **Поведение клиентов — сколько WS-соединений открывает Happ в штатном режиме?**
   - Если Happ держит 2 параллельных WS (например, для разных протоколов или резерва) — лимит `1` будет блокировать легитимного пользователя
   - v2rayNG, v2rayN — проверить отдельно
   - Проверить reconnect-сценарий: отключение Wi-Fi → включение → сколько соединений одновременно на ~1 секунду?

2. **Совместимость Xray inbound с query-параметром**:
   - Xray inbound `wsSettings.path = "/vpnws"` — сравнивает ли он путь строго или по prefix?
   - Если строго: `/vpnws?sid=abc` ≠ `/vpnws` → запрос уйдёт в 404
   - **Решение:** Nginx/Node.js проксирует в Xray уже с чистым `/vpnws` (без query) — query-параметр обрабатывается только на уровне ограничения

3. **Nginx `limit_conn` по query-параметру**:
   - `limit_conn_zone $arg_sid zone=sid:10m;` — это штатный механизм, должен работать
   - Но нужно проверить: при отсутствии `?sid=` (старые ссылки в soft-режиме) `$arg_sid` будет пустой строкой — все такие клиенты попадут в одну зону и будут блокировать друг друга. Решение: отдельная `location /vpnws` без limit_conn для старых ссылок в soft-режиме

4. **Grace period при переподключении**:
   - Мобильное устройство теряет связь на 2 секунды → клиент переподключается
   - Старое соединение ещё не закрыто (TCP FIN не дошёл) → новое будет отклонено
   - Нужен: `proxy_read_timeout` 30-60s + клиентская логика retry с backoff

### Дополнительные проверки

5. **Мониторинг отклонённых подключений**:
   - Nginx: `error_log` с `503` на отклонённых + кастомный access_log формат с `$arg_sid`
   - Node.js: логировать `{sid, ip, blocked: true}` для аудита
   - Без этого вы не узнаете, когда ограничение реально срабатывает

6. **UX-объяснение пользователю**:
   - Когда Happ получает `connection refused` → пользователь видит общую ошибку
   - FAQ-статья: «если видите "не удалось подключиться" — убедитесь, что VPN не активен на другом устройстве»
   - Или: детектировать «отклонение по sid» в Node.js и писать в системные события пользователя: «Обнаружена вторая попытка подключения»

## 🔧 Технические детали реализации

### Nginx (remote VPS)

```nginx
# Зона по sid
limit_conn_zone $arg_sid zone=sid:10m;

# Старые ссылки (soft-режим) — без ограничения
location = /vpnws {
    proxy_pass http://xray:10000;
    # ... обычные WS-настройки
}

# Новые ссылки с sid — с ограничением
location ~ ^/vpnws\?sid= {
    limit_conn sid 1;
    limit_conn_status 503;
    # Проксировать в Xray уже без query-параметра
    rewrite ^/vpnws\?.*$ /vpnws break;
    proxy_pass http://xray:10000;
}
```

### Node.js (local Amvera relay)

```typescript
// In-memory Map: sid → Set<socket>
const activeSids = new Map<string, Set<WebSocket>>();

upgradeHandler.on('upgrade', (req, socket) => {
  const url = new URL(req.url, 'http://localhost');
  const sid = url.searchParams.get('sid');
  
  if (sid) {
    const existing = activeSids.get(sid);
    if (existing && existing.size > 0) {
      socket.write('HTTP/1.1 503 Too many connections\r\n\r\n');
      socket.destroy();
      log.warn({ sid, ip: req.socket.remoteAddress }, 'blocked duplicate sid');
      return;
    }
  }
  
  // Проксировать в Xray с чистым /vpnws
  // ... существующий код ...
  
  // Зарегистрировать сокет
  if (sid) {
    if (!activeSids.has(sid)) activeSids.set(sid, new Set());
    activeSids.get(sid)!.add(ws);
    ws.on('close', () => {
      activeSids.get(sid)?.delete(ws);
      if (activeSids.get(sid)?.size === 0) activeSids.delete(sid);
    });
  }
});
```

### Генерация sid

- Вариант 1: **UUID ключа** — проще всего, не нужна отдельная сущность
- Вариант 2: **короткий opaque token** (16 символов base62) — не светить UUID в URL (хотя он и так в VLESS ссылке)
- **Важно:** sid должен быть непредсказуемым (crypto.randomUUID или secure random), чтобы его нельзя было подобрать перебором

## 🎯 Рекомендация

**Берём этот план.** Это именно тот уровень абстракции, который нужен: ограничиваем не физическое устройство (невозможно) и не IP (невидим за прокси), а **количество одновременных WebSocket-соединений на ключ** — что для подавляющего большинства клиентов эквивалентно одному устройству.

### Порядок реализации:

1. **День 1:** Проверить поведение Happ/v2rayNG (сколько WS-соединений)
2. **День 2:** Проверить Xray inbound с query-параметром (возможно, нужен rewrite)
3. **День 3:** Реализовать в Node.js relay (local Amvera) + тесты
4. **День 4:** Настроить Nginx limit_conn (remote VPS) + тесты
5. **День 5:** Обновить генерацию VLESS-ссылок + self-updating subscription
6. **День 6:** Soft-режим (старые ссылки работают без ограничения) + мониторинг
7. **День 7:** Canary на себе (подключиться с двух устройств) → hard-режим

### Важное дополнение:

Добавьте **админ-метрику**: «сколько раз сработал блок по sid за день». Если цифра близка к нулю — шаринга почти нет, и всё решение было превентивным. Если высокая — проблема реальная, и можно ужесточать (например, grace period меньше, или бан после N блокировок).

Это решение закрывает вопрос шаринга без архитектурных жертв. Отличная работа.
