# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
## Проект: VPNexus (Vibe-Proxy-Nexus)
## Задача: «Баланс как платёжное средство» — оплата подписок и услуг с внутреннего баланса пользователя
**Версия ТЗ:** 1.0 · **Статус:** к разработке · **Приоритет:** высокий

---

## 1. Контекст и цель

Сегодня внутренний баланс (`users.balanceKopecks`) расходуется только на почасовой тариф (SMART). Месячные подписки, доп. слоты и доп. трафик оплачиваются только внешними контурами (ЮMoney авто / СБП вручную с модерацией). При этом баланс пополняется реферальными комиссиями и остатками — эти деньги «заморожены».

**Цель:** сделать баланс универсальным платёжным средством внутри сервиса:
1. Оплата месячной подписки с баланса (мгновенно, без модерации).
2. Оплата доп. слота устройства и доп. трафика с баланса.
3. Автопродление месячной подписки с баланса (opt-in).

**Бизнес-эффект:** замыкается реферальная экономика (комиссия → подписка), снижается churn, уменьшается нагрузка на ручную модерацию СБП.

## 2. Объем работ и фазы

| Фаза | Состав | Оценка |
| :--- | :--- | :--- |
| **Фаза 1** | Оплата monthly + слотов + трафика с баланса | 2–3 дня |
| **Фаза 2** | Автопродление с баланса (opt-in) + уведомления | 1–2 дня |
| **Фаза 3** | Тесты, документация, деплой | 1 день |

**ВНЕ объема (v1):** комбинированная оплата (баланс + доплата СБП), конвертер «баланс → скидка», возвраты во внешние контуры.

## 3. Фаза 1. Оплата с баланса

### 3.1. Изменения API-контракта (`lib/api-spec/openapi.yaml`)

> ⚠️ Правило проекта: openapi.yaml — источник истины. После правки: `pnpm --filter @workspace/api-spec run codegen`. Файлы под `generated/` вручную не редактировать.

1. **`PaymentProvider`**: добавить значение `balance`:
   ```yaml
   enum: [manual_sbp, yookassa, yoomoney, freekassa, balance]
   ```
   (`freekassa` остаётся legacy-read-only; `balance` — платежи, создаваемые сразу `confirmed`.)

2. **`SubscriptionInput`**: добавить опциональное поле идемпотентности:
   ```yaml
   clientRequestId: { type: string, format: uuid }  # защита от двойного списания при ретраях клиента
   ```

3. **`POST /api/subscriptions`** — новое поведение при `provider: "balance"`:
   - `400` — план hourly (почасовые активируются без платежа, как сейчас);
   - `400` — план неактивен;
   - `402 { error: "insufficient_balance", balanceKopecks, requiredKopecks }` — недостаточно средств;
   - `200/201 CheckoutResult` — подписка активна, `payment` ≠ null (provider=`balance`, status=`confirmed`).
   - Повторный запрос с тем же `clientRequestId` → вернуть результат первого платежа, **не списывая повторно**.

4. **`POST /api/extra-slot-order`** и **`POST /api/extra-traffic-order`**: добавить опциональный `provider` (`balance` по аналогии). Ответы дополнить полем `paidFromBalance: boolean` (по аналогии с `freeGranted` — мгновенная выдача без checkout-флоу).

5. **`PATCH /api/me/auto-renew`** (Фаза 2): `{ enabled: boolean }` → `{ autoRenewFromBalance: boolean }`. Поле `autoRenewFromBalance` добавить в ответ `GET /api/me` (билдер `meResponse.ts`).

### 3.2. Изменения схемы БД (`lib/db/src/schema/`)

```ts
// users.ts
autoRenewFromBalance: boolean("auto_renew_from_balance").notNull().default(false),

// payments.ts — если provider хранится как enum-колонка, добавить 'balance'
// + колонка идемпотентности:
clientRequestId: text("client_request_id"),
```

- **Уникальный частичный индекс** `payments_client_request_id_unique` на `client_request_id` (WHERE client_request_id IS NOT NULL) — оформить в **`heal-schema.mjs`** (соглашение проекта: уникальные индексы — только там, чтобы `drizzle-kit push` не падал в интерактивный промпт).
- После правки схемы: `pnpm --filter @workspace/db exec tsc -p .`, затем `pnpm --filter @workspace/db run push` (dev). В проде миграцию выполнит `entrypoint.sh`.

### 3.3. Backend-логика (`artifacts/api-server/`)

**Общая функция** `lib/balancePayment.ts` (новая):
```ts
payFromBalance(userId, { type, amountKopecks, description, clientRequestId?, apply: (tx) => Promise<void> })
```
Требования к реализации:
1. **Одна транзакция БД**: `FOR UPDATE` на строку `users` → повторная проверка баланса → списание `balanceKopecks` → insert `balance_transactions` (`type: 'debit'`, `paymentId`, `description`) → insert `payments` (`provider: 'balance'`, `status: 'confirmed'`, `confirmedAt: now`) → вызов `apply()` (активация подписки / выдача слота / трафика).
2. **Идемпотентность**: при наличии `clientRequestId` — сначала SELECT существующего платежа; найден → вернуть как есть без списания.
3. **Активация подписки** — переиспользовать цепочку `startsAt/endsAt` из `lib/confirmPayment.ts` (честное продление от даты окончания текущей). Не дублировать логику — вынести общее в общую функцию.
4. **Реферальная комиссия**: при оплате подписки с баланса начисляется рефереру **так же**, как при внешних оплатах (продуктовое решение, см. §7 — открытый вопрос №1).
5. Баланс не может уйти в минус (Zod/проверка в транзакции).
6. **Не создавать** pending-платежей для `balance` — только мгновенный confirmed. В очередь модерации админки такие платежи не попадают.

**Точки входа:** `routes/subscriptions.ts`, `routes/extraSlotOrder.ts`, `routes/extraTrafficOrder.ts` — ветка `provider === "balance"` вызывает `payFromBalance`.

### 3.4. Frontend (`artifacts/vpn-portal/`)

Стиль: русский текст, чёрно-оранжевая палитра, острые углы, без эмодзи (дизайн-система проекта).

1. **`pages/checkout`**: блок «Оплатить с баланса»:
   - баланс ≥ цены → оранжевая кнопка «Оплатить с баланса (N ₽)», мгновенный переход на dashboard с success-баннером;
   - баланс < цены → строка «На балансе X ₽ — не хватает Y ₽» + ссылка «Пополнить» (ведёт на `/balance-topup`).
2. **`pages/slot-checkout`**, **`pages/traffic-checkout`**: аналогичная кнопка при достаточном балансе.
3. Генерация `clientRequestId`: `crypto.randomUUID()` на клиенте при входе в checkout, сохраняется в state до успешной оплаты (не меняется при ретраях).

### 3.5. Админ-панель

- `AdminPayment.provider = "balance"` → бейдж «Баланс» в очереди/истории платежей.
- Убедиться, что счётчик `pendingPayments` на дашборде не учитывает balance-платежи (они всегда confirmed).

## 4. Фаза 2. Автопродление с баланса (opt-in)

### 4.1. Логика (`lib/subscriptionLifecycle.ts`)

В джобе истечения подписок, **перед** отзывом ключей для месячной подписки:

```
ЕСЛИ user.autoRenewFromBalance = true И user.isBanned = false:
    ПОПЫТКА payFromBalance(userId, цена плана, source: 'auto_renew')
    УСПЕХ  → подписка продлена (новая строка, цепочка startsAt), 
             user-уведомление "auto_renew_success" {planName, amountRub, newEndsAt}
    НЕУДАЧА (не хватает средств) → штатное истечение + 
             user-уведомление "auto_renew_failed" {planName, requiredRub, balanceRub}
```

- **Однократность**: продление происходит в момент перехода `active → expired`; повторный запуск джоба не должен продлевать дважды (гарантируется тем, что старая подписка уже `expired`, а новая — отдельная строка).
- Hourly-подписки не трогаем (уже балансовые).
- Uведомления — через существующий механизм `system_events` с `userId` (схемы `UserNotification` + acknowledge уже есть).

### 4.2. Frontend

- **`pages/profile`** (или dashboard): тумблер «Автопродление с баланса» + пояснение «Спишем стоимость тарифа с баланса в день окончания подписки. Если средств не хватит — подписка просто завершится».
- Баннер/список уведомлений отображает `auto_renew_success/failed` (использовать существующий UI уведомлений).

## 5. Сквозные требования

1. **Транзакционность**: каждое списание — атомарно (п. 3.3). Никаких «списали, но не активировали».
2. **Аудит**: каждое движение — в `balance_transactions` с человекочитаемым `description` («Оплата тарифа STANDART», «Автопродление PREMIUM», «Доп. слот устройства»).
3. **Логирование**: pino-warn при отклонённых попытках оплаты с баланса (insufficient_balance) — для аналитики спроса.
4. **Безопасность**: `requireAuth` + проверка `isBanned` на всех новых ветках; Zod-валидация всех входов.
5. **Документация**: обновить `README.md`, `docs/SYSTEM_OVERVIEW.md`, `PROJECT_MAP.md` (соглашение проекта — держать docs актуальными).
