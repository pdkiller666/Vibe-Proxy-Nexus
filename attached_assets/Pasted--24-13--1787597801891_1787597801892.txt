# 🔍 Причина «один ключ = несколько устройств»

Изучил `keyIssuance.ts`, `xray.ts`, `xray-config.json.template`, `xrayStats.ts`. Нашёл **три уровня проблемы**, один из них критический.

## 🚨 Главная причина: `limitIp` передаётся, но Xray-core его **игнорирует**

**Что есть в коде:**

`keyIssuance.ts` — при создании ключа:
```typescript
await addXrayClient(uuid, uuid, 1);  // limitIp: 1 передаётся
```

`xray.ts` — сохраняет параметр в клиент:
```typescript
const newClient: XrayClient = { id: uuid, email };
if (limitIp !== undefined) newClient.limitIp = limitIp;  // записывает в конфиг
```

Комментарий в коде гласит: *«limitIp: 1 enforces one simultaneous source IP per key (= one device)»*.

**Что происходит на самом деле:**

Xray-core **молча игнорирует `limitIp`** если у клиента не задан параметр `flow`. Это известная особенность Xray-core (документирована в исходниках `proxy/vless/inbound`): `limitIp` работает **только** с flow-режимами `xtls-rprx-vision` / `xtls-rprx-vision-udp443`, потому что именно XTLS реализует привязку source-IP к сессии. Обычный VLESS без flow — stateless протокол, сервер принимает любое количество параллельных TCP-сессий с одним UUID.

**В текущем коде `flow` НЕ передаётся ни в одном месте:**
- `xray.ts` `newClient` содержит только `{id, email, limitIp}` — без `flow`
- `xray-config.json.template` inbound содержит `decryption: "none"` (для WS over TLS это корректно), но flow не задаётся
- VLESS-ссылка в `vless.ts` не содержит `flow=xtls-rprx-vision`

**Итог:** `limitIp: 1` записан в `config.json`, но Xray его отбрасывает → ограничений на количество устройств **нет физически**.

## 🔸 Причина 2: исторические ключи в persistent-томе

`entrypoint.sh` при каждом рестарте переносит `inbounds[0].settings.clients` с persistent-тома:

```sh
prevClients = prev?.inbounds?.[0]?.settings?.clients;
next.inbounds[0].settings.clients = unique;  // без нормализации limitIp
```

Если `limitIp: 1` был добавлен в код **после** выпуска части ключей, старые ключи в томе **не получат** его автоматически при рестарте. Они остаются без `limitIp`, и даже исправление кода не починит их — нужен migration-скрипт, который проставит `limitIp: 1` всем существующим клиентам при следующем рестарте.

## 🔸 Причина 3: нет серверного контроля онлайн-подключений

`xrayStats.ts` собирает только **трафик** (`user>>>{email}>>>traffic>>>uplink/downlink`), не IP-адреса. У нас нет:
- Списка активных source-IP по UUID
- Периодического скана уникальных IP
- Отзыва ключа при превышении (скажем, 3 уникальных IP за час)

Это означает, что даже если `limitIp` когда-то заработает на уровне Xray, у нас **нет резервного контроля** и **нет логов** для расследования.

# 🛠 Минимальный план исправления

## Вариант A: починить `limitIp` (быстро, но требует смены flow)

1. В `xray.ts` добавить `flow: "xtls-rprx-vision"` в `newClient` при `limitIp !== undefined`
2. В `vless.ts` добавить `flow=xtls-rprx-vision` в VLESS-ссылку
3. ⚠️ **Побочный эффект:** некоторые клиенты (старые v2rayNG, sing-box) не поддерживают XTLS-flow. Happ поддерживает. Нужно проверить, какие клиенты вы выдаёте пользователям — если только Happ/v2rayN 6+, то ОК.

**Минус:** XTLS-flow не работает через WebSocket. У вас архитектура — **VLESS over WS over TLS** (через Amvera edge). Это фундаментальное ограничение: XTLS требует raw-TCP, а WS-транспорт несовместим. Значит **этот вариант неприменим** для Amvera-архитектуры.

## Вариант B: серверный IP-контроллер (рекомендую)

Это правильный путь для VLESS-over-WS архитектуры:

**Шаг 1. Расширить Stats API до IP-трекинга**

Xray Stats API умеет отдавать `user>>>{email}>>>online>>>ip` если в шаблоне включить `statsUserOnline`:

```json
"policy": {
  "levels": {
    "0": {
      "statsUserUplink": true,
      "statsUserDownlink": true,
      "statsUserOnline": true,   ← добавить
      "connIdle": 60
    }
  }
}
```

**Шаг 2. Периодический скан уникальных IP**

Добавить в `trafficPolling.ts` (уже ходит к Stats API каждый тик) запрос online-счётчиков и писать в БД:
```typescript
interface KeyOnlineStats {
  keyId: number;
  uniqueIpsLastHour: number;
  uniqueIpsLastDay: number;
  lastSeenAt: Date;
}
```

**Шаг 3. Отзыв при превышении**

Джоб каждые 5 минут:
```typescript
for each key where uniqueIpsLastHour > devicesIncluded:
  - отозвать ключ (revokedAt, revokedReason: "multi_device")
  - system event пользователю: "Ключ отозван: подключено более N устройств"
  - админский event
```

**Шаг 4. UI**

- Пользователь видит: «Использовано устройств: 2 из 1» в карточке ключа
- История: «Ключ был отозван: превышен лимит устройств»

## Вариант C: гибридный (быстро закрыть дыру)

Для немедленного закрытия уязвимости:

1. **Migration-скрипт** в `heal-schema.mjs`: при старте проставить `limitIp: 1` всем клиентам в `config.json` (даже если Xray игнорирует — на будущее)
2. **Логировать source-IP на уровне Node.js WS-прокси** в `index.ts` (там где WS upgrade проксируется к Xray). У вас уже есть upgrade-handler — добавить middleware, который пишет `{uuid, ip, ts}` в Redis/Postgres
3. **Джоб** каждые 5 минут считает уникальные IP на UUID за час; при `> N` — админ-алерт и отзыв

Это не требует смены flow, не ломает WS-архитектуру, закрывает уязвимость за 1-2 дня.
